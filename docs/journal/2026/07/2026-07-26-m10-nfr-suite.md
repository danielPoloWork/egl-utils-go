# 2026-07-26 — Milestone 10.10: the NFR suite (two NFRs do not hold)

## What got done

- **Roadmap 10.10** (branch `feat/nfr-suite`): benchmarks for NFR-01/02/03/04/06, the §5 methodology, and
  a nightly tracking workflow. **New [ADR-0037](../../../adr/0037-nfr-benchmark-methodology.md)** and a
  full [benchmark report](../../../benchmarks/2026-07-26-nfr-suite.md) with a verdict per NFR — the point
  of the item being to say which requirements the library *meets*, not merely that benchmark functions
  exist.
- **The organising decision: split the suite by the kind of claim each NFR makes.** Some NFRs are
  properties of the code and hold on every machine; others are throughput and latency figures that depend
  on the hardware. So: **hardware-independent properties are hard gates** in the ordinary test suite
  (NFR-01's allocation budget, NFR-04's ±1% accuracy — exact, because ratelimit's clock is injected —
  and NFR-05's zero-allocation steady state), while **throughput and latency are measured and reported,
  not gated**.
- **The nightly job reports; it does not fail.** Spec §5 says ">10% regression fails"; that is recorded as
  a deliberate deviation. A hard threshold needs a stable baseline on pinned hardware, and shared
  GitHub runners move microbenchmarks by tens of percent between identical runs — a gate that fires on
  noise gets switched off and takes the honest signal with it (the same argument ADR-0036 used for
  coverage). The roadmap line itself already said "flags", so the deviation is consistent with the plan.
  The statistically defensible way to actually *fail* — benchmark base and HEAD on the **same runner in
  one job**, so noise is common-mode — is written down in the ADR as deferred rather than dismissed.

## The three findings worth acting on

- **NFR-01's "0 allocs/op" cannot be achieved.** Attributed by measuring each operation in isolation:
  `context.WithValue` (1), `r.WithContext`'s shallow Request copy (1), and each `Header.Set`'s stored
  `[]string` (1) are structural — any middleware that propagates a value through the context and writes a
  response header allocates. A target that can only fail enforces nothing, so the measured floor is
  pinned as an **enforced budget** (`TestNFR01AllocationBudget`) that fails when the count *grows*. That
  converts a dead target into a live gate. The spec target needs amendment.
- **`middleware.HeaderName` is not canonical, and it costs 2 allocations per request.** It is
  `"X-Request-ID"`; Go's canonical form is `"X-Request-Id"`, so `textproto.CanonicalMIMEHeaderKey` builds
  a fresh string on every `Get` and every `Set`. Measured directly: `Get` 1 → 0 allocs, `Set` 2 → 1 alloc
  with the canonical spelling, and **no wire-format change** (net/http canonicalises when writing).
  Deliberately *not* fixed here: 10.10 is the measurement item, and the constant's value is API-visible
  under v1 stability. Left to the maintainer with its numbers.
- **NFR-06 fails architecturally, which is exactly what 10.11 needs.** Reads average 79 ns; adding 10%
  writes takes the mean to 350 ns — a 4.4× penalty — because a single `sync.RWMutex` means every `Set`
  serialises all eight readers. 10.11's brief is to shard "only if the bench demands": **the bench
  demands it.** The Get-only/mixed gap is the number to re-measure after any sharding change. (Caveat
  carried in the report: this box has 4 cores against the reference machine's 8, so 8 goroutines are 2×
  oversubscribed.)

## Measurement traps hit, and why each is now documented in the code

Every one of these cost real time and would otherwise be rediscovered:

- **The clock cannot measure these tails on Windows.** `time.Now()` looks like it costs ~5 ns because it
  reads a periodically-updated value, and **100% of adjacent `Now`/`Since` pairs read exactly 0 ns** — so
  the first Submit benchmark reported a p99 of exactly **0 ns**. It is also bimodal under load: a
  busy-spin probe reads 3–12 µs, occasional samples differ by the 100 ns QPC tick, yet most spaced calls
  do not advance for ~1 ms. **Three guards were needed** before the suite stopped publishing artifacts as
  data — a probed resolution let "p99 = 4988 ns/op" through (a clean multiple of the tick), counting
  distinct values let it through (hundreds of batches on *different* multiples give hundreds of distinct
  values), and the *smallest* inter-sample gap let it through (one lucky 100 ns pair suffices). What works
  is the **median positive gap** between sorted samples; below 20× finer than the median sample, the
  benchmark reports `tail-unmeasurable` and publishes nothing.
- **Dead-code elimination silently reported 0 allocations** for `r.WithContext` because I discarded the
  result. Package-level sinks fixed it. I nearly published that zero.
- **An undrained pubsub fan-out benchmark measures nothing.** `Publish` drops on a full buffer (ADR-0006),
  so ten real drainers run throughout, the benchmark asserts `delivered + dropped == 10 × publishes`, and
  the reported figure counts **deliveries**.
- **NFR-04 first showed a uniform −1.00% deviation at every rate** — the signature of a harness bug, not a
  defect. Two causes: the bucket starts *full*, so an idle first window wastes its refill against the cap
  (correct token-bucket behaviour), and the initial burst is capacity rather than throughput and must be
  subtracted. Draining at t=0 and correcting the accounting gave exactly 0.0000% at every rate, including
  a fractional 12.5/s.
- **An `httptest.NewRecorder` per iteration would have been attributed to the middleware** — the same
  mistake caught in 10.4, avoided here with a discarding writer.
