# 2026-07-30 — 13.9: six lines, and the constraint that made them wait

**`v2.0.0` is tagged and pushed** (the agent's carry-through per
[release.md](../../workflow/release.md) §8, on master `b732098`; CI drafted the GitHub Release, Publish
is the maintainer's). With the tag in place, **13.9 became possible and Milestone 13 is complete.**

Both submodules now `require github.com/danielPoloWork/egl-utils-go/v2 v2.0.0` and import
`…/v2/pkg/health`. That is four import lines and two `go.mod` lines. What the item actually
demonstrates is why those six lines could not be part of the major.

## The block was concrete, not stylistic

Before the tag existed:

```
go: github.com/danielPoloWork/egl-utils-go/v2@v2.0.0: invalid version: unknown revision v2.0.0
```

After it:

```
github.com/danielPoloWork/egl-utils-go/v2 v2.0.0
```

Same command, twenty minutes apart. [ADR-0040](../../adr/0040-contrib-submodules.md)'s "require the
**released** core" is what put those twenty minutes in the middle of a milestone, and it is worth
being precise about the value it bought, because the alternative was *more* convenient in every
respect except the one that matters:

**With the rejected `replace ../..`, this migration could have shipped at any point during the major
and CI would have been green the entire time** — while the `require` line consumers actually resolve
went unexercised, because `replace` is ignored for anyone who depends on the module. The constraint
that delayed the item is the same one that makes it *verified* when it lands. A green `contrib` job
today means what a consumer's `go get` will do, not what a workspace does.

So the delay was never a cost to be minimised. It is a milestone outliving its own release, and
yesterday's release cut recorded it as such rather than papering over it — which is also why
`consistency_lint` was right to refuse the claim that M13 was complete at 13.10.

## The migration used the guide it published

I ran the `sed` snippet from the v2.0.0 release notes rather than hand-editing four imports, because
**contrib is that guide's first real consumer** and a migration guide nobody has executed is a
guess. It worked, and it confirmed the one thing that snippet is careful about: the rewrite is
anchored on the **closing quote**, so

```
"github.com/danielPoloWork/egl-utils-go/contrib/redishealth"
```

is left alone. A pattern anchored on `…/egl-utils-go/<lowercase>` — the obvious first draft — would
have produced `…/v2/pkg/contrib/redishealth`, breaking the module's reference to *itself* while the
core imports looked fine.

## One side effect invisible in the diff

`go mod tidy` raised `pgxhealth`'s transitive **`golang.org/x/sync` from v0.17.0 to v0.22.0**, because
the core v2 requires the newer pin and MVS takes the maximum. Nothing in `pgxhealth`'s own code
changed. Worth recording as a general fact: **a dependency's major bump moves a submodule's indirect
graph even when the submodule does not move**, so "we only changed two lines" is not the same as "the
build graph only changed two lines".

`go mod edit -require` also appends into whichever `require` block came last, so the direct dependency
landed among the indirects; `go mod tidy` does not regroup it. Authored the block by hand and
re-tidied to confirm it stays.

## A pre-existing advisory, measured rather than mentioned

`govulncheck` on `pgxhealth` reports **GO-2026-5970** (infinite loop on invalid input in
`golang.org/x/text@v0.29.0`) as **uncalled**. It is **not** introduced here — master's pre-13.9
`go.mod` pinned the same version, and `x/text` arrives via pgx, not via the core.

The useful part is the number nobody had: **the fix, `x/text@v0.39.0`, declares `go 1.25.0`, which is
already `pgxhealth`'s floor — so taking it is floor-safe and costs nothing.** That is the opposite of
the ADR-0024 episode, where the fix for an uncalled advisory would have raised the module floor and
was declined for exactly that reason. Left for Dependabot (it has a per-submodule entry) rather than
folded into this PR, since an indirect bump is not what 13.9 is.

## Deliberately not done

**The `contrib/*` modules are not tagged here.** ADR-0040 keeps their releases a separate act, and the
version is a maintainer's call — `v0.2.0` (a dependency change on a v0 module) or `v1.0.0` (the
modules have been stable since 10.13 and now sit on a released major). Until one of those tags exists,
a consumer's `go get` of contrib still resolves `v0.1.0`, which requires the core's **v1** — so this
migration is real in the repository and not yet real for consumers. Stating that plainly rather than
implying the item shipped end-to-end.

Also unchanged, by design: `contrib`'s module paths and tag scheme. **A contrib path carries its own
major, not the core's**, so `contrib/redishealth` stays `contrib/redishealth` while depending on the
core's v2 — the suffix rule is per module, and ADR-0040 anticipated exactly this.
