# 2026-07-26 — Milestone 10.7: fuzzing (and a contract violation it found)

## What got done

- **Roadmap 10.7 fuzzing** (branch `feat/fuzzing`): `FuzzConfigLoader`, `FuzzValidatorTags`, committed
  seed corpora, and a CI `fuzz` job spending spec v2 §7's 10-minute budget. **New
  [ADR-0034](../../../adr/0034-fuzzing-strategy.md)**.
- **The trap flagged last session was real, and shaped the whole design.** `validator.Struct` **panics
  by contract** on tag misuse (ADR-0023), so a naive `FuzzValidatorTags` asserting "never panics" fails
  within seconds on *correct* behaviour. The invariant is instead contract-shaped: any panic must be a
  string prefixed `validator: ` and **never a `runtime.Error`** — a nil dereference, index-out-of-range
  or slice-bounds violation is a genuine defect, and that type assertion is the discriminator between
  defect and contract. Any non-panic error must be a `ValidationErrors`. This is strictly stronger than
  a crash-only property, because it also catches the *opposite* bug: a malformed tag **silently
  accepted** with neither panic nor error.
- **A resource hazard that dictated the tag-space design.** Injecting a tag needs a run-time type from
  `reflect.StructOf`, and **reflect caches every type it constructs and never evicts**. Feeding
  unbounded tag text in would allocate a fresh permanently-cached type per execution — at the ~20 k
  exec/s the target actually reaches, a 5-minute run would build millions of types and OOM the runner.
  So the tag is assembled from ≤ 3 fragments of a fixed 16-entry table, bounding distinct types to
  ~45 000 (flat memory), while the field *value* is fuzzed freely because that costs nothing. Evidence
  the bound is right rather than merely safe: the corpus **saturated at ~205 interesting inputs and
  stopped growing** — the bounded space explored exhaustively, not a starved fuzzer. The ADR records
  this as load-bearing, because the obvious "improvement" is an out-of-memory kill.
- **The fuzz target found a real contract violation in `config.Load`.** Its godoc has always promised
  "The zero T is returned alongside any error" — but it returned the decode target, and both
  `encoding/json` and `gopkg.in/yaml.v3` populate the fields they read *before* the one that fails.
  Verified concretely: `{"addr":"kept","port":"not-an-int"}` produced `{Addr:"kept", Port:0}` — a
  half-configured struct escaping behind an error, with the risk that a security-relevant setting is
  silently left at its zero value. Every error path now returns the zero value. Confirmed the fix is
  necessary by reverting just the JSON branch and watching the new regression test fail with exactly
  that value. Logged under `Fixed`: a bug fix, not a breaking change, since the documented behaviour was
  always the zero value.
- **The corpus is hand-authored, not harvested.** A fuzz run produces hundreds of cache entries, but
  they are mutation artifacts — mostly random bytes picked for coverage, carrying no intent a reader can
  maintain. The 60 committed files are instead deliberately hostile documents: YAML anchor/alias
  expansion bombs, a self-referential alias, merge keys, 200-deep nesting in both formats, duplicate
  keys, tab indentation, a UTF-8 BOM, invalid UTF-8, NUL bytes, integer overflow, unterminated and
  nested `${...}` expansions, plus full coverage of the tag grammar's valid and malformed shapes.
  Generated reproducers still get committed *when a run finds one* — that is when a mutation artifact
  has earned its place, and the CI job uploads it as an artifact so a CI-only crash stays reproducible.
- Both targets ran clean before merge: **`FuzzValidatorTags` 1.65 M executions**, **`FuzzConfigLoader`
  ~51 k**. The 400× gap is the file write — `Load` takes a path, so each execution writes a file.
  Rejected extracting a byte-oriented `config.Decode` to avoid it: that would add public API purely to
  serve a test, and the file read is part of what §7 asks to be fuzzed. Mitigated instead by allocating
  the paths **once per worker process** (`f.TempDir`, not `t.TempDir`).
- **Local-toolchain finding worth carrying forward:** `-fuzz` rebuilds the instrumented standard
  library, so it needs the assembler headers under `GOROOT/pkg/include` and `GOROOT/src/runtime/cgo`.
  The portable Go in `%TEMP%` was pruned of both — complete enough for `build`, `vet`, `test` and
  `bench`, but unable to fuzz. Restored them from the distribution archive (the original zip had itself
  been temp-cleaned mid-session, so it was re-downloaded) rather than ship fuzz targets that had never
  been executed. Like `-race`, CI remains the authority.
- Local gauntlet green (portable Go 1.26.5): build, `go vet ./...`, full `go test ./...` (60 corpus
  entries included, sub-second), gofumpt clean, golangci-lint v2 0 issues, govulncheck 0 affecting,
  `consistency_lint.py` OK. No dependency change.
