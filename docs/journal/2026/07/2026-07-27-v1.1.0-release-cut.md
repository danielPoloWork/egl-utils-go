- **The release notes state two things as known-and-deliberate**, because both came out of 10.10's
  measurements and both remain open decisions for the maintainer rather than defects to hide:
  - **NFR-01's "0 allocs/op" is unachievable.** `context.WithValue`, `http.Request.WithContext` and
    each `Header.Set` allocate structurally, so any middleware that propagates a value through the
    context and writes a response header allocates. The measured floor is enforced as a ratchet budget
    instead; the specification target needs amending.
  - **`middleware.HeaderName` is `"X-Request-ID"`, not Go's canonical `"X-Request-Id"`**, costing two
    allocations per request inside `textproto.CanonicalMIMEHeaderKey` with no difference on the wire.
    Measured but not changed: an API-visible constant under the v1 commitment.
- **`contrib/redishealth` and `contrib/pgxhealth` are explicitly *not* released by this tag.** They are
  separate modules with their own driver dependencies and tag independently as
  `contrib/<name>/vX.Y.Z`; the release notes, the changelog entry and ADR-0040 all say so, because a
  reader would otherwise reasonably assume `v1.1.0` covered everything in the repository.
- Full gauntlet green: build, `go vet ./...`, full `go test ./...`, gofumpt clean, golangci-lint v2 0

## How the next session resumes

**The agent's remaining carry-through is the tag, and only after the release PR is merged to master**
(release protocol §8 — this is the agent's job, not the maintainer's):

```bash
git checkout master && git pull --ff-only     # confirm the release commit is on master
git tag -a v1.1.0 -m "<headline>"
git push origin v1.1.0
```

CI then opens the GitHub Release as a **draft**, and the **maintainer clicks Publish** — that human
checkpoint is never the agent's to take. Never tag before the merge; never publish; never amend or
delete a published tag (an *unpublished* tag whose release run failed may be deleted and re-pushed).
