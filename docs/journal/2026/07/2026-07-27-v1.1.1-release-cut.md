# 2026-07-27 — v1.1.1 release cut: a patch that was supposed to need a major

## What got done

- **`master` went green first.** The BUG-0001 fix merged as `dd452a7` and its CI run came back
  `completed/success` with **0 failing jobs** — `race` and `quality` included. First clean master
  since 2026-07-26, and the first execution of those assertions under the real detector.
  *(The monitor I armed to watch it was broken: it shelled out to standalone `jq`, which is not
  installed here — every earlier use had been `gh --jq`, gh's built-in. Forty iterations of silence
  that looked like waiting. Checked directly instead.)*

- **The maintainer asked whether v1.2.0 was due; it was not, and the reason is structural.** MINOR
  needs additive API, and there is none pending — ADR-0030's bucket 1 was the entire additive
  backlog and Milestone 10 consumed all thirteen items into v1.1.0. Bucket 2 is breaking by
  construction, bucket 3 is deviations kept. A v1.2.0 needs capability nobody has planned yet.

- **But a v1.1.1 was sitting there, and it overturns something we had been carrying since 10.10.**
  The `middleware.HeaderName` allocation cost has been recorded in three documents as *"measured but
  not changed, since it is an API-visible constant under the v1 commitment"* — deferred to a `/v2`
  that ADR-0041 and ADR-0042 both call unscheduled. **That conflated two different things.** The
  two allocations come from passing a non-canonical key to `Header.Get`/`Set`, which makes
  `textproto.CanonicalMIMEHeaderKey` allocate. The *value* of the exported constant and the *cost of
  using it as a map key* are separable, and only the first is a compatibility question.
- **So: an unexported `canonicalHeaderName = "X-Request-Id"` for map access, `HeaderName` untouched.**
  Nothing observable changed — `Header.Set` already canonicalised before storing, so the map and the
  wire have been `X-Request-Id` all along. Measured, hardware-independent: `RequestID` **6 → 4**
  allocs, `Chain` **8 → 6**, `ChainWithLogger` **11 → 9**, `RequestIDGenerated` **7 → 5**.
  [ADR-0044](../../../adr/0044-canonical-header-key-for-map-access.md).
- **The ratchet was lowered and proved to bind.** `allocBudget` goes to RequestID 4, Chain 6,
  ChainWithLogger 9; dropping RequestID to 3 fails the gate. A ratchet left slack after an
  improvement silently re-admits the regression it just removed.
- **The latency gain is reported, not claimed.** ~675 ns for the non-logging chain against 938 ns,
  consistent with two fewer allocations — but `ChainWithLogger` ranged 3.2–15.7 µs across three runs
  on this box. ADR-0037's own methodology gates the hardware-independent numbers and reports the
  rest; the allocation counts carry this.
- **Three documents that said "blocked behind a major" were corrected** — ROADMAP's M10 preamble,
  ADR-0037's deferred list *and* its rejected-alternative paragraph (annotated as "correct
  conclusion, faulty middle step" rather than rewritten), and the NFR report, updated in place per
  the 10.11 precedent so before/after sits in one document. The v1.1.0 release notes keep their
  original wording: they describe what shipped then and are not retconned.
- **Release cut per `release.md` steps 1–5:** `version.go` → 1.1.1, README badge, `[Unreleased]`
  *moved* into `docs/changelog/v1/v1.1.1.md` leaving the empty skeleton plus an index row,
  `docs/releases/v1.1.1.md` written and indexed, and **BUG-0001's `fixed-in` finally resolved from
  the placeholder `unreleased` to `v1.1.1`**. The lockstep gate was verified live rather than
  trusted: reverting `version.go` to 1.1.0 fails it on all three edges.

## How the next session resumes

**The agent's carry-through after the merge** (release.md §8, the agent's job): tag `v1.1.1` on
master and push it, which drafts the GitHub Release; the maintainer clicks Publish. Never tag before
the merge, never publish.

```bash
git checkout master && git pull --ff-only
git tag -a v1.1.1 -m "<headline>" && git push origin v1.1.1
```

**Worth noticing about this release.** Two of today's items — BUG-0001 and this one — were both
findings *recorded correctly and then inherited without re-reading*. BUG-0001's alloc assertions had
been failing in a job nobody could run locally; the HeaderName fix had been carried as blocked on an
attribution that was half right. Neither was a mistake at the time. Both survived because a written
conclusion stops being questioned once it is written down, which is the same failure the M11/M12
spec read-through kept turning up in a different costume.

Still open: the EADOS bundle's `go.yaml` profile, fixable only upstream; `egl-util-cpp`'s

## Addendum — v1.1.1 tagged; branch protection on; the NFR-01 amendment (same session)

- **v1.1.1 is out.** PR #67 merged as `f4bb0fb`; **CI was checked green on the merge commit before
  tagging** (0 failing jobs) rather than after — `release.md` §8 does not ask for that, but v1.1.0
  was tagged from a red master precisely because nobody looked, and a published tag is permanent.
  Annotated tag `v1.1.1` pushed, proxy.golang.org already serving it, GitHub Release drafted by CI.
  The maintainer's Publish is the only step left.
- **Branch protection applied to `master`** at the maintainer's request — it had been
  `404 Branch not protected`, which is how nine merges landed on a red build. 13 required checks,
  `strict`, **`enforce_admins: true`** (the failure was never a deliberate override, it was not
  noticing), reviews deliberately not required (a solo maintainer plus admin enforcement would lock
  the repo). The contexts were generated from a real run and then **diffed against that run's job
  names** — a required context no job produces leaves every PR *hanging forever* rather than
  failing, which reads as slow CI instead of broken configuration. **Renaming a CI job now means
  updating the protection in the same PR.**
- **The NFR-01 amendment turned out not to be an edit at all**, which is the part worth keeping.
  Three candidate homes, and all three were wrong for the same family of reasons:
  - `docs/specs/v2/d4np-go.md` holds the `0 allocs/op` target — but that folder is a **verbatim
    import** whose README says *"Do not edit these files"*. Editing it would destroy the provenance
    the import exists to preserve.
  - `docs/specs/02_spec_v2_gap_analysis.md` is dated 2026-07-15 and labelled *"Informational —
    records differences; adopts nothing"*. Its `🟡 never benchmarked` rows were true when written.
    Rewriting the status column would falsify the analysis that justified Milestone 10.
  - `docs/specs/01_spec_utils.md`, the frozen v1 contract, **never made the claim** — its NFR line
    is "allocation-conscious hot paths … `syncpool.BufferPool` asserts zero steady-state
    allocations", which is true and met.

  So the amendment is a **disposition**, recorded in [ADR-0030](../../../adr/0030-spec-v2-reconciliation.md)
  §3 as a maintained deviation, with a dated resolution note added above the gap analysis's table
  rather than inside it.
- **ADR-0037 had filed it in the wrong bucket, and that is now corrected too.** It said the target
  was "noted for the /v2 ledger". The ledger is for breaking changes to *our* API deferred to a
  major — but nothing about our API blocks this target, and no major release would make zero
  allocations reachable. Ledgering it would have filed it somewhere it could never be resolved.
  §3, the deviations register, is the bucket for "v2 asks X, we do Y, here is why".
- **Both of 10.10's carried-forward findings are now discharged** — this one and the `HeaderName`
  allocation cost, closed hours earlier in v1.1.1. Both had been recorded accurately and then
  inherited without re-reading: one blocked on a misattributed major, the other filed in a bucket
  that had no exit. Neither was wrong when written.

**A convention emerged today and is worth naming, because it was arrived at three separate times:**
a *drifted fact* is amended in place; a *replaced rule* is struck in place and superseded by an ADR;
a *dated analysis or verbatim import* is annotated and never rewritten. The spec's Amendments block,
ADR-0037's "correct conclusion, faulty middle step" annotation, and the gap analysis's resolution
note are the three instances.
