## A PATCH with nothing in it, and a real reason to cut it

The milestone changed no exported identifier, no behaviour, no default and no dependency. Not one
`.go` file under `pkg/` was modified in ten items. So the case for releasing had to be argued rather
than assumed, and it is a good one:

**pkg.go.dev renders documentation from the tagged tree.** The 55 runnable examples added across all
21 packages in 14.2–14.4 had been sitting in `master` for a week, invisible to everyone who does not
clone the repository, because the published version was still `v2.0.0`. The tag *is* the delivery
mechanism. That was the argument recorded when Milestone 14 was planned, and it held.

The second reason arrived later than the plan did: **the release artifacts changed.** 14.7 added a
CycloneDX SBOM with a provenance attestation, and all four earlier releases have zero assets — which
is why `release.md` step 10 had been describing something that never happened since `v0.1.0`. This is
the first tag on which that path does anything real.

## The notes lead with "no code changed", and prove it

A consumer reading "v2.0.1" asks one question before any other: *do I need to expect a behaviour
difference?* The answer here is no, so it is the first line rather than a footnote after a feature
list — with the evidence beside it: no `pkg/` file touched, surface unchanged at 141 identifiers,
`go.mod` and `go.sum` byte-identical to `v2.0.0`'s.

Two findings are carried up into the notes rather than left in the changelog, because a consumer
should not have to read a changelog to learn them:

- **NFR-06 is not met** — 887 ns against a 200 ns target. Nothing regressed; the target had never
  been verified, and the earlier "met at the mean, 46.6 ns" compared an aggregate throughput figure
  against a latency target.
- **Private vulnerability reporting was disabled**, so anyone who tried to report privately and could
  not is told plainly that it is fixed and asked to try again.

## The gate caught the last checkbox

Flipping the README milestone row to ✅ before ticking 14.12's own checkbox failed
`consistency_lint`'s `milestones` check immediately:

```
[milestones] README marks Milestone 14 complete, but ROADMAP has unchecked item(s) in that milestone
```

Exactly the drift it exists to catch, and a reminder worth keeping: **the last item of a milestone is
the one most easily left unticked**, because the person ticking it is the one who just did it.

The `version-lockstep` gate was then verified live rather than trusted, the way 13.10 did at its cut
— reverting `version.go` alone reports three failures (badge, changelog, notes), and reverting the
badge alone reports one. A green lockstep on a release PR means something only if it can go red.

## Milestone 14, closed

Ten items of adoption work and no API. In order: the examples convention and 55 examples across 21
packages; `examples/service` as its own module; the verified `contrib/*` release act; the pinned,
least-privilege, SBOM-carrying supply chain; the two NFR tails measured on Linux CI; `CONTRIBUTING.md`
and `CODE_OF_CONDUCT.md`; the additive-capability ledger; repository metadata and the doc-site
decision; and this release.

Six ADRs — 0053 through 0058.

## Next: nothing, deliberately

**Milestone 15 is not chosen, and that is the milestone's own result.** The ledger holds 49 deferred
capabilities, each with the evidence that would schedule it, and **exactly one trigger has fired**.
14.10 existed so the next milestone would come from demand rather than invention; the honest output
of that is that demand has not yet arrived, and the register now makes that a fact instead of an
impression.
