# 2026-08-08 — the hole stays open, and now it is a decision

A correction session. `v2.0.1` shipped a changelog entry announcing something that does not exist.

## What happened

14.11 drafted a GitHub Release for `v0.1.0` — the last tag without one — and left it as a draft,
because publishing is the maintainer's checkpoint. The maintainer chose **not** to publish it, and
the draft was removed.

Meanwhile `v2.0.1` had already been tagged and published, and its changelog and release notes both
announced the backfill as delivered. So five documents asserted a Release that no longer existed, one
of them a **released** record.

Verified before changing anything: no `v0.1.0` release exists at all, not even a draft, while the tag
survives at `refs/tags/v0.1.0`.

## The decision, recorded rather than reversed

Keeping it deleted is defensible and is now written down as a decision instead of surviving as an
oversight — which is the part that genuinely differs from the starting state.

`v0.1.0` predates every feature package. Its own notes say installing it is not recommended. The
record a reader actually needs is already in `docs/releases/v0.1.0.md` and
`docs/changelog/v0/v0.1.0.md`, both of which have existed since the day of the tag. What a Release
would add is a publication whose content is essentially *"do not use this"*.

The cost is stated rather than argued away: **the release history is permanently asymmetric** — five
tags, four Releases. ADR-0055's whole reason for drafting no Release for `contrib/*` tags is that
such asymmetries are easy to create and awkward to remove, so the amendment there sharpens that
argument rather than softening it.

## Correcting a released record

`docs/changelog/v2/v2.0.1.md` is the permanent record of what `v2.0.1` claimed. The entry is
therefore **left in place with a dated correction beside it**, not deleted — the same amend-in-place
convention ADR-0003 and ADR-0041 set for decision records. Deleting it would make the published
release notes and the repository disagree about what `v2.0.1` said, which is a worse problem than the
one being fixed.

The same note goes in `docs/releases/v2.0.1.md`, which shipped the same claim.

## What each document needed

| Document | Claim | Correction |
|---|---|---|
| `docs/adr/0055-…` | *"the hole is filled… all five core tags now have one"* — present tense, false | Rewritten: the hole stays open, by decision, with the reasoning |
| `docs/changelog/v2/v2.0.1.md` | announced the backfill as shipped | Dated correction beside the entry |
| `docs/releases/v2.0.1.md` | 14.11's row said "the `v0.1.0` Release backfilled" | Row reworded + a correction note |
| `docs/workflow/release.md` | *"`v0.1.0` was backfilled this way"* | Procedure kept; now opens with **decide whether it is worth publishing before drafting it** |
| `ROADMAP.md` 14.11 | as-built annotation said the Release was drafted | Followed-up note: the third deliverable did not land, and why |

The 14.11 journal entry and the journal index are **left alone**. They are dated checkpoints of what
was true that day, and rewriting history to match the present is exactly what a dated trail exists to
prevent — this entry is how the change is recorded.

## The reusable bit

`release.md`'s backfill procedure survives, with a clause in front of it that was missing:

> A backfill is worth doing when the Release adds something a reader cannot get from the repository;
> an old tag that nobody should install is the case where it does not.

The procedure was written assuming the answer was yes. The first time it was exercised, the answer
was no — and the mechanics (`--latest=false`, `--verify-tag`, draft-then-publish) are still correct
for the next time it is yes.
