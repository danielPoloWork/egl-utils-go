# Threat model — egl-utils-go

> **Owner:** the **security-auditor** role (it drafts here; findings feed the audit risk
> register). Produced and kept current by the **audit threat-modeling sub-mode**
> (`/eados security` → `/eados audit`). Method: **STRIDE**. Scaffolded empty on purpose —
> an explicit `n/a` with a reason is honest; an unexamined boundary is not.

## 1. Scope & trust boundaries

List every boundary an attacker could stand on either side of — network edges, process/privilege
boundaries, tenancy separation, third-party services — and for each: the **untrusted inputs**
that cross it, and the **assumptions** the design makes about it.

| Boundary | Untrusted inputs crossing it | Assumptions |
|---|---|---|
| **Public HTTP edge** (a consuming service's inbound requests, guarded by this module's `middleware`) | request headers (`X-Request-ID`, `Origin`, `Access-Control-Request-*`), method, path (logged by 4.2), body | TLS terminated upstream; this module is a library composed into the consumer's handler chain, not a standalone server; the consumer owns authn/authz and body-size limits |
| **Credential store** (password verification via the `hash` package) | candidate passwords at login; stored bcrypt hashes if the store leaks | the consumer stores only the hash string this package returns (never plaintext) and passes it back verbatim to verify; the CSPRNG and bcrypt come from `golang.org/x/crypto` |

_First populated by ROADMAP 4.1 (`middleware.RequestID`, ADR-0013); Milestone 4 completed the
HTTP-edge middleware (Logger 4.2, Recoverer 4.3, Cors 4.4), and Milestone 8 added the credential
store (`hash`, 8.2). Boundaries and inputs grow as the diagnostics surface (M9) lands, and Milestone
10 widened the HTTP edge with `ratelimit`'s admission middleware (10.4, ADR-0031) and made the
credential store's work factor configurable (10.5, ADR-0032); each such PR extends the rows below
rather than starting fresh._

## 2. STRIDE pass

Work the six categories (**S**-**T**-**R**-**I**-**D**-**E**) **per boundary/component** above.
Every cell gets an entry — a threat, a mitigation, or an explicit `n/a (reason)`; never a blank.

| Category | Threat considered | Boundary / component | Mitigation / control | Status |
|---|---|---|---|---|
| Spoofing — is the caller who it claims? | Caller sets `X-Request-ID` to impersonate another request's trail, or a consumer mistakes the ID for identity | HTTP edge / `middleware.RequestID` | The ID is documented (godoc + ADR-0013) as a **correlation token only, never for authn/authz**; it grants no authority, so spoofing it achieves nothing | ☑ |
| Tampering — can data/code be altered in flight or at rest? | Attacker injects CR/LF or control bytes into `X-Request-ID` to forge log lines or split response headers when the ID is echoed/logged | HTTP edge / `middleware.RequestID` | Inbound ID accepted only if visible-ASCII (`0x21–0x7e`) and ≤128 bytes; otherwise regenerated. CR/LF/NUL can never reach logs or the reflected header (ADR-0013, control C-2) | ☑ |
| Repudiation — can an action be denied for lack of a trail? | A request has no correlatable identifier, so its handling cannot be traced | HTTP edge / `middleware.RequestID` | Every request carries an ID — adopted if valid, else generated — propagated in context for downstream logging (4.2) | ☑ |
| Information disclosure — can data leak across a boundary? | A generated ID leaks server state (time, sequence, host) or is predictable | HTTP edge / `middleware.RequestID` | Generated with `crypto/rand.Text` (≥128 bits, RFC 4648 base32); derived from no server state and unguessable (ADR-0013) | ☑ |
| Information disclosure — can data leak across a boundary? | Request logging leaks secrets carried in the URL query string (tokens, API keys, signed URLs), or in headers/body, into log stores that outlive and out-scope the request | HTTP edge / `middleware.Logger` | Logger records `r.URL.Path` only — never the query string, headers, or body; the logged fields are a fixed, secret-free set (method, path, status, duration, bytes, `request_id`). A consumer needing more logs it themselves, owning that disclosure (ADR-0014, control C-2) | ☑ |
| Information disclosure — can data leak across a boundary? | A panicking handler leaks a stack trace (source paths, symbols, internal structure) or the panic value (possibly secrets in flight) into the HTTP response | HTTP edge / `middleware.Recoverer` | Recoverer writes only a generic `500 Internal Server Error` to the client; the panic value and stack are logged server-side (`slog.Default`, Error) and never written to the response. Its log line is path-only, like Logger (ADR-0016, control C-2) | ☑ |
| Spoofing / Information disclosure — can a foreign origin read cross-origin responses or send credentials it should not? | An over-broad CORS policy lets any website read authenticated responses or make credentialed cross-origin requests (e.g. `Access-Control-Allow-Origin: *` with credentials, or reflecting every `Origin`) | HTTP edge / `middleware.Cors` | Deny-by-default (`CorsConfig` zero value allows no origin); a specific allowed origin is echoed with `Vary: Origin`, `*` is emitted only without credentials, and the Fetch-forbidden credentials+`*` combination is refused at construction (panic). Subdomain/regex origin patterns are deliberately not offered (ADR-0017, control C-3) | ☑ |
| Information disclosure — can a leaked hash store or a timing side-channel reveal passwords? | A stolen password-hash store is brute-forced offline; or a non-constant-time verify leaks password bytes via timing; or over-long passwords silently collide | Credential store / `hash.HashPassword`, `hash.HashPasswordCost`, `hash.CheckPassword` | bcrypt (adaptive cost, per-hash random salt) makes offline cracking expensive; **the factor defaults to 12 — four times the work per candidate password that v1's default of 10 required** — and is this module's own constant rather than `bcrypt.DefaultCost`, so it cannot weaken through a dependency bump (ADR-0052); it is raisable further via `HashPasswordCost` with the latency cost measured per step (ADR-0032), and hashes written at an older factor keep verifying while rehash-on-login moves them up; `CompareHashAndPassword` is constant-time; input over 72 bytes is rejected (`ErrPasswordTooLong`), never truncated. bcrypt is CPU-hard but **not memory-hard**, so it resists GPU/ASIC cracking less well than argon2id — the godoc recommends argon2id for new systems and documents the verify-and-rehash migration path (ADR-0024, ADR-0032, control C-4) | ☑ |
| Information disclosure — can a health endpoint leak internal detail? | An unauthenticated `/healthz` echoes probe error text (connection strings, hostnames, backend versions) or the failing dependency's internals to anyone who can reach it | HTTP edge / `health.Handler` | The response is status-only — overall `ok`/`unavailable` plus each check's name and `ok`/`fail`; the probe's error is never written to the body (logged in-probe instead). Same no-detail-to-client posture as Logger/Recoverer (ADR-0026) | ☑ |
| Denial of service — can a probe endpoint be abused? | Unauthenticated, high-volume `/healthz` hits trigger expensive dependency probes (DB round-trips) on every request | HTTP edge / `health.Handler` | Probes run concurrently (endpoint latency = slowest probe, not the sum) and honor the request context; authentication remains the consumer's concern, while request volume can now be bounded by composing `ratelimit.(*Limiter).Middleware` in front of the probe endpoint (ADR-0031) or by network placement | ◑ partial (probe cost bounded per request; applying the rate limiter is the consumer's composition choice) |
| Denial of service — can metric labels be exploded? | A client sends arbitrary request methods (or the app labels by raw path) so an unbounded number of time series is allocated, exhausting memory | HTTP edge / `(*metrics.Recorder).Middleware` | The request path is never a label; the `method` label is normalized to the nine known HTTP methods plus `"other"`, so client-controlled input cannot inflate cardinality — the label set is bounded by construction (ADR-0027). Since ADR-0050 the series live in a map **this module owns**, so the bound is arithmetic rather than an argument about label domains: ten method values by the 100–999 status codes `net/http` admits is **at most 9 000 series**, whatever traffic a Recorder is shown (`TestSeriesCountIsBoundedByConstruction`) | ☑ |
| Denial of service — can the password work factor be weaponised? | Verification costs the same as hashing at the same factor, and every login attempt — including failed ones, on an endpoint an unauthenticated caller can reach — pays it. A cost chosen purely for offline-cracking resistance multiplies the CPU an attacker consumes per request (measured: at cost 12, ~4.3 verifications/second saturate one core). **From `/v2` this is the default rather than an opt-in** (ADR-0052), so a deployment inherits the trade-off instead of choosing it | Credential store / `hash.HashPassword`, `hash.HashPasswordCost`, `hash.CheckPassword` | The trade-off is measured and documented rather than hidden: the [cost-sizing report](../benchmarks/2026-07-26-hash-bcrypt-cost-sizing.md) gives per-cost latency so a deployer sizes against a real budget, and the godoc directs them to rate-limit the login endpoint. The mitigation composes in-module — `ratelimit.(*Limiter).Middleware` (ADR-0031, control C-5) sheds over-budget requests before the handler runs. **Because the strong factor is now the default, the godoc states its cost at `HashPassword` itself and names the mitigation there** rather than only in the package overview — a deployment that reads nothing still meets the number where it calls the function, and can drop to cost 10 explicitly if its login path cannot absorb it. The accepted range's ceiling (31) is documented as bcrypt's hard limit and explicitly *not* a recommendation (~32 h/hash) (ADR-0032) | ◑ partial (trade-off measured and mitigable; applying admission control, and overriding the default if it does not fit the login budget, are the deployment's) |
| Tampering / Information disclosure — can a weak work factor be introduced silently? | A misconfigured cost (a zero value from an unset config field, or a value someone lowered) produces a hash that is orders of magnitude cheaper to crack while looking entirely normal — the store is weakened with no error and no signal | Credential store / `hash.HashPasswordCost` | The floor is enforced **in this module rather than delegated**, because upstream is unsafe here: `bcrypt.GenerateFromPassword` silently promotes a cost below its `MinCost` of 4 to the default (discarding the caller's intent without a word) and honours costs 4–9 verbatim. An out-of-range cost returns `ErrInvalidCost` naming the value and produces no hash at all; the upstream behaviour is pinned by a test so the guard cannot rot (ADR-0032, control C-4) | ☑ |
| Tampering — does a fixed cost weaken over time? | Hardware improves, so the same work factor gets cheaper every year: a configuration that was adequate at deployment silently degrades, and hashes already in the store never improve on their own | Credential store / `hash.Cost` | Named as an operational risk rather than glossed: the documentation prescribes periodic cost review against a re-run of the benchmark, and `Cost` (~112 ns) plus verify-and-rehash-on-login is the mechanism to move a store forward without a flag day. **The library default has now moved once (10 → 12 at `/v2`, ADR-0052), which makes the review a demonstrated practice rather than a stated intention** — and because raising a default quadruples every login's CPU, it is major-only, so a deployment that wants to move sooner uses `HashPasswordCost` rather than waiting for a library bump. The residual — users who never log in again keep old hashes — is stated explicitly so it is paired with a dormant-account policy (ADR-0032) | ◑ partial (mechanism and guidance provided; the review schedule and dormant-account policy are the consumer's) |
| Spoofing — can login errors enable user enumeration? | Distinct responses for "no such user" vs "wrong password" let an attacker enumerate valid accounts | Credential store / `hash.CheckPassword` | A wrong password returns the generic `ErrMismatch`; the godoc directs callers to surface only a generic failure to the end user, never revealing which of identifier or password was wrong (ADR-0024) | ☑ |
| Denial of service — can the surface be exhausted? | Oversized or high-volume `X-Request-ID` headers inflate memory and log storage; an unrecovered handler panic drops the connection and can unwind past the handler | HTTP edge / `middleware.RequestID`, `middleware.Recoverer` | 128-byte cap on the adopted ID bounds per-request cost (RequestID); Recoverer contains a handler panic and turns it into a bounded 500 rather than a dropped connection or a crash. Request *rate* is now addressable in-module via `ratelimit.(*Limiter).Middleware` (ADR-0031); body-size limits remain the consumer's concern (`http.MaxBytesReader`) | ◑ partial (per-request panics contained, IDs bounded, request rate available; body-size DoS deferred to consumer) |
| Denial of service — can request volume exhaust the service? | High-volume traffic saturates handlers, connections, and downstream dependencies faster than they can serve it | HTTP edge / `ratelimit.(*Limiter).Middleware` | Admission is gated by the token bucket and over-budget requests are **shed immediately** (429 + `Retry-After`) rather than queued — the middleware uses `Allow`, never `Wait`, so a burst cannot convert into an unbounded queue of parked goroutines and held connections (ADR-0031, control C-5). The admit path allocates nothing, so the guard itself is not a cost amplifier | ◑ partial (total throughput bounded; per-client fairness deferred to consumer — see the row below) |
| Denial of service — can one client consume everyone's budget? | A single abusive caller drains the shared bucket, so the limiter refuses legitimate clients while the attacker keeps the whole allowance (and `X-Forwarded-For` spoofing would defeat a naive per-IP fix) | HTTP edge / `ratelimit.(*Limiter).Middleware` | Documented limitation, deliberately not papered over: one limiter bounds **total** throughput, not any client's share. Per-key limiting needs a key-extraction policy (which header is trustworthy depends on the consumer's proxy topology) and an eviction policy for idle keys; presuming either would silently create an IP-spoofing bypass or a memory leak. The godoc and ADR-0031 direct consumers to keep a limiter per key and gate with `Allow` | ◑ partial (accepted risk; per-key policy is the consumer's decision, deferred and additive) |
| Information disclosure — can a refusal leak limiter state? | A 429 reveals the configured rate, burst, or instantaneous bucket level, letting an attacker tune traffic to sit just under the threshold | HTTP edge / `ratelimit.(*Limiter).Middleware` | The body is the generic status text and the only quantitative hint is `Retry-After: ceil(1/rate)` — a constant computed once per decorator, deliberately not the tighter `(1-tokens)/rate`, so the live bucket level never crosses the boundary. Same no-detail-to-client posture as Recoverer/health (ADR-0031) | ☑ |
| Denial of service — can a refusal be turned into a log flood? | The traffic being limited drives one log line per denial, so an attacker inflates log volume and cost through the very control meant to protect the service | HTTP edge / `ratelimit.(*Limiter).Middleware` | The middleware logs **nothing**; a denial is a normal operating condition, not a fault, and is observable as an ordinary 429 through `middleware.Logger` under the consumer's own logging policy. Deliberately unlike `Recoverer`, which logs a genuine bug (ADR-0031) | ☑ |
| Elevation of privilege — can a caller gain authority it was not granted? | Caller uses the request ID to gain access | HTTP edge / `middleware.RequestID` | n/a — the ID confers no authority by construction; RequestID makes no authorization decision | ☑ |

## 3. Findings → the risk register

A threat that survives analysis lands in the audit **risk register** with its severity
(low/medium/high/critical), affected component, realistic impact, and a concrete mitigation — the
same record shape the audit phase emits. A confirmed, reproducible defect additionally becomes a
[bug-ledger](../bugs/README.md) record; a vulnerability needing coordinated disclosure becomes a
**draft** advisory the human publishes.
