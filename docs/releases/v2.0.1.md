# v2.0.1 — Milestone 14: adoption, the release act, and the supply chain

**Date:** 2026-08-08 · **Milestone:** M14 — Adoption: examples, the release act, and the supply chain

## No code changed

Say it first, because it is the first thing a consumer reading "v2.0.1" wants to know: **upgrading
from `v2.0.0` cannot change how your program runs.**

- No `.go` file under `pkg/` was modified in this milestone.
- The exported surface is unchanged at **141 identifiers**.
- No behaviour changed, no default changed, no error text changed.
- `go.mod` and `go.sum` are byte-identical to `v2.0.0`'s — still the same three runtime dependencies.

```bash
go get github.com/danielPoloWork/egl-utils-go/v2@v2.0.1
```

There is no migration, and nothing to test differently.

## So why cut a release at all?

Because two things only reach a consumer through a tag.

**1. pkg.go.dev renders documentation from the tagged tree.** Milestone 14 added **55 runnable
examples across all 21 packages** — every one executed by `go test` with its output verified, so they
cannot rot into fiction. They have been in `master` for a week and invisible to everyone who does not
clone the repository, because the published version was still `v2.0.0`. **This tag is what publishes
them.** That was the argument for scheduling a release at the end of a milestone that deliberately
added no API, and it is the whole payload.

**2. The release artifacts changed.** From this version each release carries a CycloneDX SBOM with a
provenance attestation ([ADR-0056](../adr/0056-build-time-supply-chain.md)). It is the **first
artifact ever attached to a release of this project** — the four earlier releases have none — so
`v2.0.1` is where that machinery first does something real rather than being described.

## Two findings a consumer should read

**NFR-06 is not met.** 14.8 measured the cache's mixed-load p99 at **887 ns against a 200 ns
target**, with oversubscription removed entirely, so the shortfall is the code's latency under
concurrent load and not the runner's core count. Nothing regressed — the target had never been
verified, and the earlier claim that it was "met at the mean, 46.6 ns" compared an aggregate
*throughput* figure against a *latency* target. `GetHit` uncontended is 32.9 ns and inside the
target; the same `Get` under an 8-way mix occupies ~775 ns. Which of those the NFR means is an open
spec question. NFR-02's `Submit` p99 **is** met, at 176 ns against 2 µs.

**If you tried to report something privately and could not, that is now fixed.** Private
vulnerability reporting was disabled on the repository while `SECURITY.md` — and, since 14.9,
`CODE_OF_CONDUCT.md` — both directed reporters to that form. It is enabled.

## Verifying the SBOM

```bash
gh release download v2.0.1 --repo danielPoloWork/egl-utils-go --pattern '*.cdx.json'
gh attestation verify egl-utils-go-v2.0.1.cdx.json --repo danielPoloWork/egl-utils-go
```

What that proves: *this document* came from *this workflow* at *this commit*. What it does not
prove: anything about the module you resolve — that is `sum.golang.org`'s job, and your `go.sum`
already carries the hash it publishes. The attestation exists because the SBOM is a new artifact with
no other origin story, not because the module needed one.

The document lists **three** components — `golang.org/x/crypto`, `golang.org/x/sync` and
`gopkg.in/yaml.v3` — because it inventories the *runtime* graph, which is exactly what a consumer
links. That is [ADR-0004](../adr/0004-runtime-dependency-policy.md)'s dependency policy in
machine-readable form.
