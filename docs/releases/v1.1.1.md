# v1.1.1 — Two allocations per request, and a CI gate that had stopped guarding

**Date:** 2026-07-27 · **Milestone:** none (patch)

A performance fix and a repair, neither of which changes the public surface. `go doc` reports the
same 130 exported identifiers as v1.1.0, `go.mod` and `go.sum` are untouched, and upgrading needs
no consumer change.

## The fix: a canonical header key

`middleware.RequestID` now reaches the header map through the canonical spelling of the header
name. `http.Header`'s `Get` and `Set` both run `textproto.CanonicalMIMEHeaderKey` on the key they
are handed, and that allocates a fresh string whenever the key is not already canonical — Go
title-cases each dash-separated token, so the canonical form is `"X-Request-Id"` and
`"X-Request-ID"` is not it. Two allocations per request, for nothing.

| Benchmark | allocs/op | was |
|---|---|---|
| `RequestID` (inbound ID adopted) | **4** | 6 |
| `RequestIDGenerated` (ID minted) | **5** | 7 |
| `Chain` (RequestID + Recoverer + Cors) | **6** | 8 |
| `ChainWithLogger` | **9** | 11 |

Bytes per operation fall with them (`RequestID` 432 → 400 B). The NFR-01 ratchet is lowered to the
new floor and verified to bind there — dropping `RequestID` to 3 fails the gate. Latency improved
too (~675 ns for the non-logging chain against 938 ns), but this workstation's spread is wide
enough that the allocation counts, which are hardware-independent, carry the result.

**`middleware.HeaderName` is unchanged.** It is still exported, still `"X-Request-ID"`, and nothing
observable differs — `http.Header.Set` already canonicalised the key before storing, so the header
map and the bytes on the wire were `X-Request-Id` before this release too. A consumer calling
`Get(middleware.HeaderName)` is unaffected.

That distinction is the whole reason this is a patch. Milestone 10.10 measured these two
allocations and recorded the fix as blocked behind a MAJOR-only change to the exported constant —
and carried that framing through the ROADMAP, the NFR report and the v1.1.0 release notes. The
attribution was half right: the cost was real, the blocker was not. The constant's *value* and the
*cost of using it as a map key* are separable, and only the first is a compatibility question.
[ADR-0044](../adr/0044-canonical-header-key-for-map-access.md) records it.

## The repair: `-race` had stopped guarding anything

CI's `race` and `quality` jobs had failed on **every push since 2026-07-26 — the v1.1.0 release
commit included**. No data race was ever involved
([BUG-0001](../bugs/2026/07/BUG-0001-race-detector-breaks-allocation-and-pool-identity-assertions.md),
the bug ledger's first record). Four assertions measured allocation counts and `sync.Pool` object
identity, both of which the race detector deliberately perturbs, so they described an instrumented
binary rather than the one you run.

They are now excluded from `-race` builds with `//go:build !race`, on dedicated files so the
exclusion shows up in a directory listing. **Every one still gates** — they run in the ordinary
`go test ./...` on all four CI cells; only the two `-race` jobs skip them. Nothing that can
usefully run under the detector was taken from it.

Raising the budgets to accommodate the detector was rejected: it would have masked the real
regressions the ratchet exists to catch. The fix is test-only and no library behaviour was
affected — but for a day, the jobs guarding this library's headline property were reporting noise,
which is worth stating plainly in the release that repairs them.

## Upgrading

Nothing to do. No exported identifier changed, no dependency moved, no behaviour differs.

The `contrib/*` submodules version independently (ADR-0040) and are unaffected; they were released
separately as `contrib/redishealth/v0.1.0` and `contrib/pgxhealth/v0.1.0`.
