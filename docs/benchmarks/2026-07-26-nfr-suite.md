# Benchmark Report: the NFR suite (NFR-01 … NFR-06)

- **Date:** 2026-07-26
- **Version / commit:** v1.0.0 + unreleased M10 work (branch `feat/nfr-suite`, roadmap 10.10; parent
  `master` @ `5f51186`)
- **Environment:** Intel Core i5-6600K @ 3.50GHz (**4 cores, no SMT**), 32 GB RAM, Windows 10 Pro
  (10.0.19045), go1.26.5 windows/amd64, default (release) build. Developer workstation — informational,
  not a gating baseline. Spec §5 names a Ryzen 7 5800X (8 cores / 16 threads) as the reference machine,
  which this is not; the core-count gap matters for NFR-02 and NFR-06 and is called out where it does.
- **Command:** `go test -run '^$' -bench NFR -benchmem -count 5 ./middleware/ ./workerpool/ ./pubsub/ ./cache/`

## Scenario

Spec v2 §5 states six numeric non-functional requirements. This report measures all of them and gives
each a verdict, so the milestone's claim to "have" an NFR suite rests on numbers rather than on the
existence of benchmark functions.

The suite separates the NFRs by what kind of claim they make, because that decides how each can be
enforced:

| Kind | NFRs | Enforcement |
|---|---|---|
| **Hardware-independent** — a property of the code | NFR-01 allocations, NFR-04 rate accuracy, NFR-05 allocations | **Hard assertion in the test suite**, on every CI cell |
| **Hardware-dependent** — throughput and latency | NFR-01 latency, NFR-02, NFR-03, NFR-06 | Measured and tracked; reported nightly, not gated (ADR-0037) |

## Results

Median of 5 runs; spread is min–max.

### NFR-01 — middleware chain ≤ 1 µs and 0 allocs/op; Logger ≤ 3 allocs/op

> **Updated 2026-07-27 (v1.1.1, [ADR-0044](../adr/0044-canonical-header-key-for-map-access.md)).**
> The original measurement below found two of `RequestID`'s allocations came from a non-canonical
> header key and recorded the fix as blocked behind an API-visible change to the exported
> `HeaderName`. **It was not blocked:** the constant's *value* and the *cost of using it as a map
> key* are separable, so the middleware now takes the canonical spelling through an unexported
> constant and `HeaderName` is untouched. Both sets of numbers are kept here so the before/after
> sits in one place.

#### As first measured — non-canonical header key (roadmap 10.10)

| Benchmark | ns/op | B/op | allocs/op |
|---|---|---|---|
| `Chain` (RequestID + Recoverer + Cors) | **937.8** (929–1084) | 584 | **8** |
| `RequestIDOnly` (inbound ID adopted) | 638.7 (610–823) | 432 | 6 |
| `RequestIDGenerated` (ID minted) | 756.8 (749–908) | 464 | 7 |
| `RecovererOnly` | 52.7 (50–57) | 48 | 1 |
| `CorsOnly` | 218.9 (212–263) | 110 | 1 |
| `CorsPreflight` (terminal OPTIONS) | 652.7 (639–698) | 332 | 3 |
| `Logger` (discarding slog JSON handler) | 1250 (1228–1260) | 48 | **1** |
| `ChainWithLogger` | 2740 (2732–2770) | 1089 | 11 |

**Verdict: latency met, allocations not met — and the allocation target is unachievable.**

- Latency: 938 ns for the non-logging chain, inside the 1 µs budget with ~6% of headroom. Thin, and
  worth watching.
- Logger: 1 alloc/op against a ≤ 3 budget. **Met**, with room.
- Allocations: 8/op against a target of **0**. Attributed by measuring each structural operation in
  isolation (with a package-level sink, since discarding the result lets the compiler elide the
  allocation and report a spurious zero):

  | Operation | allocs |
  |---|---|
  | `context.WithValue` | 1 — how the ID propagates at all |
  | `r.WithContext` (shallow `*http.Request` copy) | 1 — must not mutate the caller's Request |
  | `Header.Set`, the `[]string{value}` it stores | 1 per header written |
  | `Header.Get` with a **non-canonical** key | 1 |
  | `Header.Set` with a **non-canonical** key | 1 extra |
  | `crypto/rand.Text` (mint path only) | 1 |

  Any middleware that propagates a value through the context and writes a response header allocates.
  **Zero is not reachable**, so the suite pins the measured floor as an enforced *budget* instead — a
  ratchet that fails when the count grows (`TestNFR01AllocationBudget`). ADR-0037 records the target as
  needing amendment.

**Actionable finding — acted on in v1.1.1.** `middleware.HeaderName` is `"X-Request-ID"`, which is not
Go's canonical form (`X-Request-Id`), so `textproto.CanonicalMIMEHeaderKey` builds a fresh string on
**every `Get` and every `Set`** — 2 of the 6 allocations in `RequestID`, buying nothing. Measured
directly: 3 allocs / 369.9 ns for a non-canonical `Set`+`Get` pair against 1 alloc / 198.2 ns for the
canonical one. The wire format is unaffected, because `net/http` canonicalises header names when
writing, so the header on the wire is `X-Request-Id` either way.

10.10 recorded this as blocked behind an API-visible change to the exported constant and left it to
the maintainer. **That attribution was half right:** the cost was real, the blocker was not — the
constant's value and the cost of using it as a map key are separable, and only the first is a
compatibility question. See [ADR-0044](../adr/0044-canonical-header-key-for-map-access.md).

#### After the canonical-key fix (v1.1.1, ADR-0044)

Same workstation, 3 runs; allocations are hardware-independent, the timings are not.

| Benchmark | allocs/op | was | B/op | was |
|---|---|---|---|---|
| `Chain` (RequestID + Recoverer + Cors) | **6** | 8 | 547 | 584 |
| `RequestIDOnly` (inbound ID adopted) | **4** | 6 | 400 | 432 |
| `RequestIDGenerated` (ID minted) | **5** | 7 | 432 | 464 |
| `ChainWithLogger` | **9** | 11 | 1063 | 1089 |
| `RecovererOnly`, `CorsOnly`, `Logger` | 1 | 1 | — | unchanged |

**Two allocations removed from every request through `RequestID`**, and the ratchet in
`allocBudget` is lowered to the new floor (RequestID 4, Chain 6, ChainWithLogger 9) — verified to
bind there, since lowering RequestID to 3 fails the gate.

**The latency improvement is reported, not claimed.** The non-logging chain measured ~675 ns against
938 ns before, which is consistent with removing two allocations, but this workstation's spread is
wide enough to swamp the signal — `ChainWithLogger` ranged 3.2–15.7 µs across the same three runs.
Per this document's own methodology, hardware-dependent timings are reported and hardware-
independent allocation counts are gated; the allocation numbers carry this result.

### NFR-02 — workerpool ≥ 1 M no-op tasks/s at 8 workers; Submit p99 ≤ 2 µs

| Benchmark | ns/op | tasks/s | allocs/op |
|---|---|---|---|
| `Throughput` (empty task) | 226.1 (181–253) | **4.42 M** (3.95–5.52 M) | 0 |
| `ThroughputCounted` (atomic per task) | 320.7 (289–348) | 3.12 M (2.87–3.47 M) | 1 |
| `SubmitP99` | 215.2 (200–245) | — | 0 |

**Verdict: throughput met by 4.4×; tail unverified.** 4.42 M tasks/s against a 1 M target, on *half* the
reference machine's cores. The counted variant confirms every task ran (it fails the benchmark
otherwise) and costs ~95 ns of atomic, so 3.12 M is a floor rather than a competing figure.

The **p99 could not be measured on this platform** — see *Measuring a tail* below. The benchmark reports
`tail-unmeasurable=1` rather than a number.

### NFR-03 — pubsub ≥ 500 k msgs/s to 10 subscribers, 64 B payload

| Benchmark | ns/op | delivered/s | drops/publish |
|---|---|---|---|
| `FanOut` (publish + drain, 10 subscribers) | 1573 (1503–1630) | **6.33 M** (6.13–6.57 M) | 0.009 (0–0.12) |
| `PublishOnly` | 1538 (1399–1672) | — | 0.035 (0–0.88) |
| `FanOutFiltered` (accept-all filter) | 1671 (1667–1704) | — | 0 (0–0.077) |

**Verdict: met by 12.7×.** 6.33 M delivered messages/s against a 500 k target.

The number counts **deliveries, not publishes**, which matters here: `Publish` never blocks on a slow
subscriber and drops instead (ADR-0006), so a benchmark publishing into undrained subscriptions would
measure the drop path and report a magnificent figure for delivering nothing. Ten real drainers run for
the whole measurement, the benchmark asserts `delivered + dropped == 10 × publishes`, and drops are
reported. The residual drop rate (~0.9% of deliveries at the median) is consumer-side saturation on 4
cores, not broker loss.

### NFR-04 — ratelimit admission within ±1% over a 10 s bursty pattern (burst = 2 × rate)

| Rate | Admitted | Measured rate | Deviation |
|---|---|---|---|
| 10/s | 120 (burst 20 + 100 refilled) | 10.0000/s | **+0.0000%** |
| 100/s | 1200 (200 + 1000) | 100.0000/s | **+0.0000%** |
| 1000/s | 12000 (2000 + 10000) | 1000.0000/s | **+0.0000%** |
| 12.5/s (fractional) | 150 (25 + 125) | 12.5000/s | **+0.0000%** |

**Verdict: met exactly, and gated.** This is the one NFR that is hardware-independent: the limiter's
refill is computed from an injected clock (ADR-0012), so advancing fake time by 10 s exercises exactly
the arithmetic the requirement is about. It is therefore a **test with a hard assertion**
(`TestNFR04AdmissionRateAccuracy`) rather than a benchmark, and it runs on every CI cell. A companion
test asserts the limiter never admits *more* than the bucket can fund — running fast is a broken rate
limit, not a fast one.

Two accounting traps, both of which first presented as a uniform −1.00% "deviation" at every rate — a
systematic error identical across rates is the signature of a harness bug, not a defect:

1. The bucket starts **full**, so an idle first window wastes its refill against the cap
   (`min(burst, tokens + elapsed × rate)` discards it, which is correct token-bucket behaviour). The
   harness now drains the initial burst at t=0 so what follows measures the refill *rate* rather than
   the capacity.
2. The initial burst is capacity, not throughput, so it must be subtracted before comparing against the
   configured rate.

### NFR-06 — cache.InMemory Get p99 ≤ 200 ns at 1 M entries, 90/10, 8 goroutines

> **Updated 2026-07-26 (roadmap 10.11).** The original measurement below found NFR-06 not met and
> identified the cause; the cache was then sharded (ADR-0038) and re-measured. Both sets of numbers are
> kept here so the before/after sits in one place.

#### As first measured — single `sync.RWMutex` (roadmap 10.10)

| Benchmark | ns/op (mean) | allocs/op |
|---|---|---|
| `GetOnly` (1 M entries, 8 goroutines) | **78.9** (76–81) | 0 |
| `Mixed` (90/10 read/write) | **349.8** (325–371) | 0 |
| `GetTail` (90/10, batch-sampled) | 310.9 (284–312) | 0 |

**Verdict at the time: not met, and the reason architectural.** Reads alone average 79 ns, comfortably
inside 200 ns. Adding 10% writes took the mean to **350 ns — a 4.4× penalty** — because `Cache` was one
`map` behind one `sync.RWMutex`: every `Set` took the exclusive lock and serialised all eight readers.

**This was the evidence roadmap 10.11 was told to gather.** Its brief was to shard "only if the bench
demands"; the bench demanded it.

#### After sharding — 32 independently locked shards (roadmap 10.11, ADR-0038)

Median of 5 on the same machine, same benchmarks:

| Benchmark | Before | After | Change |
|---|---|---|---|
| `NFR06Mixed` (90/10, 8 goroutines, 1 M) | 349.8 ns | **46.6 ns** | **7.5× faster** |
| `NFR06GetOnly` (8 goroutines, 1 M) | 78.9 ns | **57.7 ns** | 1.4× faster |
| `GetParallel` (4 threads) | 59.7 ns | 56.1 ns | 1.06× faster |
| `GetHit` (uncontended) | 27.2 ns | 32.9 ns | **21% slower** |
| `GetMiss` (uncontended) | 15.1 ns | 20.1 ns | **33% slower** |
| `Set` (uncontended) | 52.0 ns | 60.5 ns | **16% slower** |

**Verdict: met at the mean.** The 90/10 mix now averages **46.6 ns** against a 200 ns target, and is no
longer slower than the read-only path — which is itself the evidence that write contention has stopped
being the bottleneck.

**The uncontended paths got slower, by about 5 ns**: the cost of the `maphash.Comparable` call that picks
a shard. In relative terms that is a 16–33% regression on single-threaded use, and it is a real cost to a
consumer using one cache from one goroutine. Accepted because the absolute figure is ~5 ns against a
~300 ns saving on the contended path, and because a cache in this library exists to be shared. ADR-0038
records the trade so it can be revisited rather than rediscovered.

Two caveats stand on the p99 question: this box has **4 cores against the reference machine's 8**, so
eight goroutines are 2× oversubscribed and pay scheduling costs the reference would not; and the tail
figures are wall-clock batch means (see below), not per-operation percentiles. **NFR-06's p99 as such
remains unverified on this platform** — the mean is what improved 7.5×.

## Measuring a tail — why two of these are unverified

NFR-02 and NFR-06 state **p99** targets of 2 µs and 200 ns. Go's benchmark framework reports means, so
percentiles need per-operation sampling, and that ran straight into the platform's clock. Measured, not
assumed:

- `time.Now()` appears to cost **~5 ns**, because on Windows it reads a value the OS updates
  periodically rather than querying a counter.
- **100% of adjacent `Now()`/`Since()` pairs read exactly 0 ns.** Per-operation sampling of a
  sub-microsecond operation therefore yields all zeros: the first version of the Submit benchmark
  reported a p99 of exactly **0 ns**, which looks spectacular and measures nothing.
- The clock is **bimodal under load**. A busy-spin probe reads 3–12 µs; occasional adjacent samples
  differ by the 100 ns QPC tick; yet most spaced `Now()` calls do not advance for ~1 ms, so many batches
  time as 0 while others land on millisecond multiples.

Three successive guards were needed before the suite stopped publishing artifacts as data. Checking a
separately probed resolution let a p99 of "4988 ns/op" through (a clean multiple of the tick). Counting
distinct sample values let it through too — hundreds of batches on *different* multiples of one tick
produce hundreds of distinct values. Taking the *smallest* gap between samples let it through as well,
because one lucky 100 ns pair is enough. What works is the **median positive gap** between adjacent
sorted samples: it describes the granularity that actually governed the data. When that granularity is
not at least 20× finer than the median sample, the benchmark reports `tail-unmeasurable=1` and publishes
no percentile.

Tails are therefore sampled in **batches** (1000 operations, per-operation mean), which understates the
true tail — one 50 µs stall inside a 1000-operation batch lifts that batch's mean by 50 ns instead of
appearing as an outlier — and makes the figure a sound *regression detector* and a lower bound, not a
percentile. On Linux, where `clock_gettime` resolves to tens of nanoseconds, the same code publishes
real numbers; the nightly job is where these two NFRs get judged.

## Reproduce

```bash
git checkout feat/nfr-suite   # or master once the 10.10 PR merges
# The hardware-independent gates (NFR-01 allocations, NFR-04, NFR-05):
go test ./middleware/ ./ratelimit/ ./syncpool/ -run 'NFR|Alloc' -v

# The measured suite:
go test -run '^$' -bench NFR -benchmem -count 5 \
  ./middleware/ ./workerpool/ ./pubsub/ ./cache/
```

Runtime is ~4 minutes at `-count 5`; the cache benchmarks load 1 M entries per run.
