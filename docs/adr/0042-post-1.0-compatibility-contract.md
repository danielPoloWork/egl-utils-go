# ADR-0042: State the post-1.0 compatibility contract, superseding spec §3's pre-1.0 clause

- **Status:** Accepted
- **Date:** 2026-07-27
- **Deciders:** Maintainer (Daniel Polo), with the architect agent
- **Related:** spec §3 (Compatibility), ADR-0030 (`/v2` ledger), ADR-0041, AGENTS.md §11, ROADMAP 11.2

## Context

The frozen v1 specification was rendered from the intake interview while the project was pre-1.0,
and its §3 compatibility line still reads:

> Compatibility: SemVer, pre-1.0 milestone-driven; breaking changes to the public interface require
> a MAJOR-intent note in the PR

Both halves have since stopped being true. The module released **v1.0.0** on 2026-07-15 —
"the feature-complete 1.0, committing to API stability for every exported identifier under
Semantic Versioning" — and is now at v1.1.0. More importantly, the second half describes a
*procedure that no longer exists*: under the pre-1.0 regime a breaking change was **mergeable**, on
the condition that the PR carried a MAJOR-intent note. Under the v1.0.0 commitment it is not
mergeable into v1.x at all. ADR-0030 already operates the replacement mechanism — its §2 ledger
holds seven breaking deltas that were *deferred* rather than merged with a note, including a bcrypt
default-cost change that is API-compatible and was still refused because spec §5 counts documented
behaviour as breaking surface.

So the stale clause is not a stale number. Every other divergence found in this sweep (the language
floor, the coverage percentage, the goleak hedge) was a fact that had drifted and could be corrected
in place under the spec's own divergence rule. This one is a governance rule that was replaced, and
a reader following the frozen text would reach a materially wrong conclusion about what may be
merged. That is what makes it the ADR branch of the rule rather than the amendment branch.

## Decision

Spec §3's compatibility clause is **superseded, not rewritten**: the original text is struck in
place and retained as the historical pre-1.0 contract, and this ADR states the contract in force.

The module is **post-1.0** and follows Semantic Versioning 2.0.0:

- **Within `v1.x`, every exported identifier is stable.** No removal, no signature change, and no
  change to documented behaviour — spec §5's own rule counts a documented behavioural contract as
  part of the breaking surface, so "API-compatible" is not sufficient grounds for a change.
- **Additions ship as MINOR**, under the additive discipline Milestone 10 demonstrated: thirteen
  items delivered in v1.1.0 with no exported signature changed.
- **A breaking change is not merged into `v1.x` under any note or annotation.** It is recorded in
  the [ADR-0030](0030-spec-v2-reconciliation.md) §2 ledger, which is the single register of what a
  future major would carry. The MAJOR-intent-note mechanism is retired with this ADR.
- **A major release takes Go's `/v2` module path rule** — `module …/v2` and a `/v2` import path.
  No `/v2` is scheduled; [ADR-0041](0041-series-logical-namespace.md) records that if one is ever
  opened, the module-path question is re-evaluated in the same breath, because that boundary is the
  only place the move is free.
- **PATCH** covers fixes that change neither the surface nor documented behaviour.

`contrib/*` submodules are outside this contract: per [ADR-0040](0040-contrib-submodules.md) they
are independent modules with independent tags, and their compatibility is their own.

## Alternatives Considered

- **Amend the clause in place**, as the language floor, coverage floor and goleak hedge were
  amended in this same PR. Rejected: those were facts that had drifted, and rewriting them loses
  nothing. This is a rule that was *replaced*, and the difference between "breaking changes are
  mergeable with a note" and "breaking changes are not mergeable" is exactly the kind of promise a
  consumer relies on. Overwriting it would erase the evidence that the promise ever changed —
  in a document whose entire purpose is to be the frozen contract.
- **Leave the clause alone and rely on ADR-0030.** Rejected: ADR-0030 records a *disposition* for
  one spec revision's deltas, not the standing compatibility rule, and nothing in the frozen spec
  points a reader to it. A frozen document that actively misleads is worse than one that is
  out of date, because "frozen" invites trust.
- **Open a `/v2` now and align the spec wholesale.** Rejected for the same reason ADR-0030 rejected
  it: it obsoletes a two-week-old 1.0 and forks the module path for corrections most consumers do
  not need. The ledger exists precisely so this stays a deliberate future choice.

## Consequences

- The compatibility promise is now stated once, in force, and reachable from the frozen spec: a
  reader of §3 sees the struck clause and the pointer here.
- **The `/v2` ledger becomes the enforcement point rather than a filing cabinet.** With the
  MAJOR-intent note retired, ADR-0030 §2 is the only sanctioned destination for a breaking change,
  and a PR proposing one has exactly one correct outcome: an entry there.
- No code, tooling, or CI change: this states a rule the project has been following since v1.0.0
  (ADR-0030's bucket 2 is the proof) rather than introducing one. Nothing in `version.go`,
  `CHANGELOG.md` or the release protocol moves.
- The spec's Amendments block now distinguishes two kinds of post-freeze edit — corrections applied
  in place, and clauses superseded by an ADR. Future divergences inherit that split: a drifted fact
  is amended, a replaced rule takes an ADR.
- AGENTS.md §11 already describes both the pre-1.0 and post-1.0 regimes correctly and needs no
  change; the ROADMAP's "Versioning start: pre-1.0 milestone-driven" line is a statement about how
  versioning *began* and remains accurate.
